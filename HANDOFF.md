## 1. What this repo is

The marketing + reference site for **Máddu** (the framework). Lives as a
sibling repo to `../maddu`, deliberately decoupled so the site can ship
public while the framework repo stays private (and vice versa).

- Stack: **Astro 5 static**, vanilla CSS + JS, self-hosted IBM Plex
- Build: 40 routes in ~9s. No SSR. Single `dist/` ships anywhere.
- Posture: **no third-party network calls at runtime** (no analytics,
  no Google Fonts, no CDN scripts). The site does what the framework
  does — the no-third-party rule applies to both.

### Late-session touch-ups (added after the original handoff draft)

- **Mermaid zoom controls now container-bounded.** Previously the
  cluster went `position: fixed` to viewport bottom-right when the
  diagram was the most-visible host. That visually escaped the diagram
  into surrounding page chrome. Now the float controller writes the
  host's overhang past viewport bottom into a `--m-ctl-offset` CSS
  variable, and the controls `translateY()` upward by exactly that —
  so they hover at the bottom of the diagram's *visible portion* but
  never leave the host's `overflow: hidden` bounds. JS in
  `src/components/Mermaid.astro :: initFloatController()`.
- **Mermaid wheel-zoom now requires Ctrl / ⌘.** Plain wheel passes
  through (page scrolls), `Ctrl + wheel` or `⌘ + wheel` zooms. One-shot
  hint pill flashes "Hold ⌘ to zoom" / "Hold Ctrl to zoom" on the first
  plain-wheel attempt.
- **Nav menu is full-width 3-col grid.** Brand left · links centered ·
  search + theme + burger right. Below 1080px, links collapse cleanly
  to burger; no half-shown items at any width.
- **Vercel config (`vercel.json`)** at repo root for the alternative
  deploy path.

## 3. Open question: should the site be public?

**Verbatim user question:** *"This is the site for Maddu, for end user
to download. But I'm not sure, since exposing source code exposes maddu
framework to risk. I'm not sure what the best approach is here. What is
your take?"*

### Claude's take (before Codex review)

The site repo is separate from the framework repo. Making this repo
public does **not** expose framework source.

What the site **does** expose:

- Architectural philosophy (the 8+1 hard rules, 13 layers, gauntlet)
- Threat model + 7 structural defenses
- The fact that 156 doctor gates run on every install
- Slash command surface (13 on-ramps), verb surface (53 verbs)

What the site does **not** expose:

- Framework source code (separate repo)
- Spine event schema details beyond the published event names
- Internal worker mechanics
- Secret-scan patterns (only the categories are named, not the regex)

**Security through obscurity is not part of Máddu's posture.** The
threat-model page is structured around "named defenses + named residual
risk." Publishing the architecture is consistent with the framework's
verifiable-not-declared principle.

**The real tension is timing, not exposure:**

- The framework repo is currently private. Users who land on
  `/install` can't actually install.
- "Coming soon" pages historically build less trust than
  "here it is."
- Going public NOW + adding marketing pressure to ship the framework
  public might be useful, OR might force the framework public before
  it's ready.

**My pre-Codex recommendation: ship the site to Vercel as a private
preview deploy** (password-protected or behind a `VERCEL_PREVIEW_ONLY`
header), share the URL with stakeholders for feedback, then flip both
the site AND the framework public simultaneously when both are ready.

## 4. Final decision (user, 2026-06-01)

> "The maddu app site is only an extension of git. More documentation
> and more in-depth explanatory. At first I won't launch it publicly
> only share it with peers."

Codex review was queued but **deliberately skipped** — user reached the
same conclusion as the pre-review recommendation, so the second opinion
wasn't load-bearing.

### What this means in practice

1. **Frame the site as documentation, not a marketing-funnel landing.**
   It's the long-form explanation of the framework's posture, threat
   model, governance, and verb ontology. The framework repo is the
   product; the site is the manual.
2. **Deploy to Vercel as a preview (not production-aliased).**
   - Push the repo to GitHub on a non-`main` branch (e.g. `preview` or
     `dev`), or push to `main` without aliasing production.
   - Vercel will issue a unique URL like
     `maddu-site-abc123.vercel.app`. That URL is hard to discover,
     `X-Robots-Tag: noindex` by default on `.vercel.app` previews,
     no search indexing.
   - Share the URL directly with peers. No password gate needed at
     this scale (preview URLs are unguessable enough for peer review).
3. **Optional belt-and-suspenders for "really not indexed":**
   - Add `<meta name="robots" content="noindex,nofollow">` to
     `Layout.astro` while in preview, drop it at public-launch.
   - Or restrict by team: invite peers to the Vercel project so the
     URL requires Vercel SSO.
4. **Hold the public flip until the framework repo is ready.** Site
   public + framework private = "coming soon" trust erosion. Site
   public + framework public = the real launch. Plan for both flips
   in the same week, not weeks apart.

## 7. Known dev-only quirks

- Vite's `node_modules/.vite/deps/` cache occasionally desyncs and
  serves a 504 "Outdated Optimize Dep" for mermaid sub-chunks
  (sequenceDiagram, flowDiagram, etc.). When you see a diagram render
  as raw source text on a dev URL, that's the cause. **Fix:**
  `Remove-Item -Recurse -Force node_modules\.vite` then `npm run dev`.
  Production builds don't have this problem.
- Two Astro dev servers running on different ports (4321 + 4322) can
  share the desynced cache via the lockfile. Kill the older one before
  clearing the cache.
